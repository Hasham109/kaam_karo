## What I built
- **Prisma 7.10.1** (`prisma`, `@prisma/client`, `@prisma/adapter-pg` pinned in the pnpm catalog; install scripts denied in `allowBuilds`, the CLI fetches the schema engine itself). `services/api/prisma.config.ts` loads the root `.env` if present.
- **Multi-file schema** `services/api/prisma/schema/`: `_base.prisma` (generator/datasource) + one file per module with a header `Module Mn <module> … Owner: A0x … ARCH §4`. Rules in `services/api/prisma/README.md`.
- **Citations everywhere.** Every model, field and enum has a `///` doc citing BP §n / D-xxx / requirement ID. The test checks that the IDs exist in DECISIONS.md, REQUIREMENTS.md and OPEN_QUESTIONS.md. `ARCH §` or `OQ-` alone does not count. Table comments are prefixed `[module <m>, owner A0x]`.
- **COMMENT ON in Postgres.** `prisma/tools/comments.ts` generates 731 statements: 53 tables, 617 columns and 61 enum types (after the review fixes; the first version had 715 = 52 + 604 + 59, the earlier "718/607" was a counting error, QA BUG-QA-T2.3-04). The init migration embeds them, and a unit test fails when the migrations' comments differ from the schema docs. For later migrations, `pnpm --filter @kaamkaro/api db:comments` prints the missing statements.
- **Module rule (INFRA-001).** FK relations exist only inside one module file (enforced by a test). Cross-module references are plain UUID columns (`serviceId`, `bookingId`, …) and are documented as "ref <module>.<table> by ID". This works safely because users are anonymised, never deleted. Shared enum types (`ActorRole`, `AppLanguage`, `SellingMode`, `VerificationLevel`, `AdminSubRole`) are used across modules.
- **PostGIS.** The migration runs `CREATE EXTENSION postgis`. It adds `geography(Point,4326)` on `address.point`, `location_snapshot.point` and `service_area.center`, and `geography(MultiPolygon,4326)` on `service_zone.area` (null = whole city, D-019). All four columns have GiST indexes.
- **Money.** Stored as `BigInt` PKR paisa in `*Minor` fields. There are no floats (enforced by a test). Rates are `Decimal(5,4)`, and only as a snapshot (`provider_ledger_entry.commission_rate`). No business value is seeded.
- **BP §26 at DB level** (`prisma/sql/20_append_only.sql`):
  - Role `kaamkaro_app` (NOLOGIN) gets DML on all tables but only SELECT/INSERT on `audit_log`, `marketplace_event`, `job_event`, `provider_ledger_entry`, `payment`, `payment_method_record` and `refund`.
  - `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE` triggers raise `kk_append_only` for every role, including the owner.
  - The `kk_ledger_check_reversal` trigger requires a reversal to have the same provider and the opposite direction, and the sum of reversals must stay ≤ the original (advisory lock against races).
  - Payment and refund status changes are new rows with the same `payment_ref` / `refund_ref`; the latest row is current. This is needed because PAY-003 requires that payment rows are never updated.
- **CHECK constraints** (`prisma/sql/10_constraints.sql`):
  - crew_size ≥ 1: on quote (required) and on booking.
  - `NO_SHOW` requires `no_show_party`.
  - Amounts > 0 or ≥ 0.
  - Ledger type ↔ direction ↔ link. There is no free-standing credit (LEDGER-PAY-006).
  - Commission-payment and dispute decisions must have decider, time and reason.
  - Rating 1–5.
  - Activation, case-update and fare-line parent rules.
  - Availability-rule and service-area shape.
  - Config scope ↔ scope_ref.
- **Partial unique indexes** (preview `partialIndexes`):
  - one `CASH_RECORDED` payment and one `SUCCEEDED` payment per booking;
  - one COMMISSION_DEBIT and one JOB_CREDIT per booking;
  - one credit per approved submission;
  - config key uniqueness for global and scoped rows.
  - In addition, `payment_method_record.booking_id` is unique (LEDGER-002 "recorded once").
- **Migration** `prisma/migrations/20261023000000_init/migration.sql`. It is generated by `node prisma/tools/db-schema.ts init` and contains, in order: extension, `prisma migrate diff --from-empty --to-schema` DDL, CHECKs, append-only block, comments. `prisma validate` passes.
- **Scripts** (`@kaamkaro/api`): `db:generate`, `db:validate`, `db:deploy`, `db:migrate`, `db:comments`, `test:db`. The turbo `build`/`typecheck`/`test` tasks depend on `db:generate`. The generated client goes to `src/generated/prisma` and is git-, eslint- and prettier-ignored. A new `tsconfig.tools.json` typechecks the tools and the DB tests.
- **CI.** New job `db-schema` in `.github/workflows/ci.yml`: a postgis/postgis:18-3.6 service runs `db:validate` → `db:deploy` → `test:db`.

## How to use it (for consumer agents)
- **Edit your module file only.** Use `///` citations and no `@relation` to another module. Then run `pnpm --filter @kaamkaro/api exec prisma migrate dev --create-only --name x` and append the `db:comments` output (README "Changing the schema").
- **Reading money:** `amountMinor` is paisa (BigInt).
- **Payment/refund state:** the latest row per `paymentRef` / `refundRef`.
- **Provider balance:** Σ credit − Σ debit on `provider_ledger_entry`. Always pass a business `idempotencyKey`.
- **A09 corrections:** insert a `REVERSAL` row with `reversesEntryId` and `reason`. The DB refuses over-reversal.
- **A04:** status changes go through your transition table. NO_SHOW needs `noShowParty`. `crewSize` on booking is nullable until acceptance. `reviewSubmittedAt` is the "Reviewed" flag.
- **T2.2 (A01):** PrismaService with `PrismaPg`. The API login must be a member of `kaamkaro_app` and not the owner (README "Database roles").

## Self-check (IMPL §9)
1. **Requirement IDs and BP sections:** listed in the header. Every model, field and enum cites BP §n, D-xxx or a requirement ID, and the test enforces it.
2. **Behaviour without a citation?** No. The test fails on any uncited doc or unknown ID.
3. **Hard-coded configurable value or vendor?** No.
   - The migration seeds no business value.
   - Rates and thresholds live only in config_rule (T2.6).
   - No vendor is chosen: gateway and payout refs are opaque strings behind the interfaces.
4. **Can a client bypass the server for status/price/permission?** No. The DB adds a second layer:
   - append-only financial and event history;
   - one cash record per booking;
   - no free-standing ledger credit;
   - CHECKs on crew size and no-show party.
5. **Urdu RTL and network failure?** No UI in this task.
   - en/ur name columns exist for city, zone, category and service.
   - `AppLanguage` is stored for the user, summaries and notifications.
   - The idempotency_key table supports safe retries (REL-008).
