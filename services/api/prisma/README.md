# Database schema (T2.3)

PostgreSQL + PostGIS with Prisma migrations (D-001). Schema v1 covers every ARCH §5 entity (BP §25, §66) except
Promotion ("discount or campaign later", BP §25; ARCH §5.1 `[NOT LAUNCH]`).

## Layout

| Path                     | What                                                                                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------- |
| `schema/_base.prisma`    | generator + datasource only                                                                          |
| `schema/<module>.prisma` | one file per ARCH §4 module; header names the module and the owner agent                             |
| `sql/00_extensions.sql`  | `CREATE EXTENSION postgis`                                                                           |
| `sql/10_constraints.sql` | CHECK constraints Prisma cannot express                                                              |
| `sql/20_privileges.sql`  | `kaamkaro_app` grants: default deny, UPDATE except append-only, DELETE allow-list (BP §26, §29)      |
| `sql/30_integrity.sql`   | append-only triggers, ledger/payment/refund insert guards, decision-freeze, location freeze (BP §26) |
| `tools/`                 | schema reader, citation rules, COMMENT ON generator, `db-schema.ts` CLI                              |
| `migrations/`            | Prisma migrations. `20261023000000_init` is generated by `node prisma/tools/db-schema.ts init`       |
| `tests-db/`              | DB tests (`pnpm --filter @kaamkaro/api test:db`, needs a migrated database)                          |

## Rules

1. **Cite or stop.** Every model, field and enum has a `///` doc that cites `BP §n`, an existing `D-xxx` or an
   existing requirement ID (`ARCH §`/`OQ-` alone do not count). `pnpm --filter @kaamkaro/api test` fails otherwise.
   The docs are written to Postgres as `COMMENT ON` and the test fails if the migrations' comments drift.
2. **No cross-module FKs.** `@relation` only between models in the same file. Another module's row is
   referenced by a plain UUID column (`serviceId`, `bookingId`, …) and read through that module's service
   (ARCH §4, INFRA-001). Users are never hard-deleted (anonymised, SEC-AUTH-008), so dangling IDs do not occur.
   Shared enum _types_ (`ActorRole`, `AppLanguage`, `SellingMode`, `VerificationLevel`, `AdminSubRole`) may be
   used across modules; they are types, not table access.
3. **Money** = `BigInt` PKR minor units (paisa), field names end in `Minor`. No `Float` columns.
4. **Append-only tables** (`tools/append-only.ts`: audit_log, marketplace_event, job_event, provider_ledger_entry,
   payment, payment_method_record, refund, config_rule): SELECT/INSERT only for the app, and triggers refuse
   UPDATE/DELETE/TRUNCATE for every role. Corrections are new rows (reversals, new config versions). Payment and
   refund status changes are new rows with the same `payment_ref` / `refund_ref`. Never put personal data in these
   rows unmasked: they cannot be anonymised later (BP §26; SEC-AUTH-008; T2.2 masker).
   Insert guards: ledger rows must match their CASH record / SUCCEEDED DIGITAL payment / APPROVED submission /
   settlement; reversals and refunds are capped; one settled payment and one job ledger entry per booking.
   Decision rows (`FROZEN_TABLES`) cannot change after the decision; confirmed location snapshots never change.
   Ledger reversals and refunds must not run under REPEATABLE READ (trigger refuses).
5. **No business values in migrations.** Config values and catalog/city seeds belong to T2.6 (A03).
6. Technical fields allowed without asking (ARCH §5): `id`, `created_at`, `updated_at`, `version`,
   `deleted_at`, `created_by`. Anything else needs a citation.

## Database roles (SEC-REVIEW-T2.3 #1, #16)

| Role                            | Env var                  | Rights                                                                                                |
| ------------------------------- | ------------------------ | ----------------------------------------------------------------------------------------------------- |
| bootstrap superuser/DBA         | —                        | runs `infra/db/bootstrap.sql` once per database: PostGIS, `kaamkaro_app`, API login, PUBLIC hardening |
| migration owner                 | `MIGRATION_DATABASE_URL` | owns the tables; used only by `prisma migrate` and `test:db`                                          |
| `kaamkaro_app`                  | —                        | NOLOGIN group role; privileges come from `sql/20_privileges.sql`                                      |
| API login (e.g. `kaamkaro_api`) | `DATABASE_URL`           | LOGIN, member of `kaamkaro_app`, not owner, not superuser, no BYPASSRLS                               |

- The API checks its login at start-up (`@kaamkaro/platform` `assertAppDbRole`, `src/db/verify-db-role.ts`) and
  refuses to start if it is a superuser, has BYPASSRLS, is (a member of) the table owner or is not in
  `kaamkaro_app`. `loadServerEnv` also refuses `DATABASE_URL` = `MIGRATION_DATABASE_URL`.
- Local docker runs the bootstrap on first start (`infra/db/init/10-bootstrap.sh`, `APP_DB_USER`/`APP_DB_PASSWORD`).
  For a volume created before T2.3 run `infra/db/bootstrap.sql` by hand (command at the top of the file).
- The migration still creates `kaamkaro_app` and hardens PUBLIC when its login has the rights (local, CI), so it
  works without the bootstrap; in staging/production the bootstrap runs first and those steps are skipped.

## Changing the schema

1. Edit `schema/<module>.prisma` (owner agent, or via REQUESTS.md) with `///` citations.
2. `pnpm --filter @kaamkaro/api exec prisma migrate dev --create-only --name <change>`.
3. Append CHECKs by hand if needed. Default privileges give new tables SELECT/INSERT only: add
   `GRANT UPDATE` for a mutable table and `GRANT DELETE` only if it joins `DELETE_ALLOWED_TABLES`. A new
   append-only table needs both triggers and an entry in `tools/append-only.ts`.
4. Append the output of `pnpm --filter @kaamkaro/api db:comments` to the new migration.
5. `pnpm --filter @kaamkaro/api test` (citations + comments) and, with a database, `db:deploy` + `test:db`.
